# E2E (Maestro) — testID conventions

## Rule

Every interactive element on a user flow gets a `testID`. When you add a
new screen, sheet, or interactive component, add `testID` in the same PR.
When you rename a flow target, grep `maestro/flows/` for the old id and
update both together — TypeScript won't catch the drift.

## Naming

- **kebab-case** throughout.
- Static: `<scope>-<role>` — `signin-submit-button`, `discover-search-input`.
- List items: `<scope>-<role>-{id}` via template literal:
  ``testID={`collection-card-${item.id}`}``.
- Tab bar: `tabbar-<route>` (`tabbar-feed`, `tabbar-camera`, …).
- Settings toggles: `settings-toggle-<SettingName>` (derives from
  `useSetting.ts` enum — renaming the enum implicitly renames the testID).
- Reusable in lists: accept `testIDPrefix` rather than guessing — see
  `ReactionBar.tsx` and `Tabs.tsx`. Caller passes
  ``testIDPrefix={`feed-item-${item.findId}-reaction`}``; the component
  emits `<prefix>-like` / `<prefix>-fire` / `<prefix>-wow`.
- Screen root: `<screen>-screen` on the `SafeAreaView`
  (e.g. `feed-screen`, `collection-detail-screen`). `SafeAreaView`
  forwards `testID` through.

## Where it goes

On the **interactive primitive** (`Pressable` / `TouchableOpacity` /
`TextInput` / `Switch`), **never** on a wrapping `<View>` that doesn't
receive the press:

```tsx
// Right
<TouchableOpacity testID="welcome-signin-button" onPress={...}>...

// Wrong — testID lands on the wrong node
<View testID="welcome-signin-button">
  <TouchableOpacity onPress={...}>...
```

For React Navigation tabs use `tabBarButtonTestID` on `Tabs.Screen` —
the underlying button is generated by the navigator, not exposed in JSX.

## What gets a testID

- **Yes:** every interactive primitive on a user flow, every screen root,
  every list item targeted by id, every state-anchor a flow needs to
  assert ("achievement sheet is open" → testID on the sheet root).
- **No:** decorative `<View>` / static `<Text>` / layout wrappers.
  Maestro should assert via `testID`, not via i18n'd copy.

## Forwarding components (no explicit `testID` in the file)

These spread `...props` onto an RN primitive, so `<X testID="..." />`
works — pass at the call site:

- `Button` → `TouchableOpacity`
- `Input` → `TextInput`
- `HapticTab` → `PlatformPressable` (in practice driven by
  `tabBarButtonTestID` on `Tabs.Screen`)
- `SafeAreaView` → explicit `testID` prop; used as screen root anchor.

State-anchor components carry an optional `testID?: string` prop the
caller passes when a flow needs it: `EmptyState`, `Spinner`, `MapPreview`,
`MapClusterBubble`, `FindMarker`, `ProgressBar`, `XpPopup`,
`AchievementSheet`, `AnalyzingOverlay`.

## Intentionally without testID

- `IconSymbol` — pure icon, no interaction; anchor on the parent.
- `share/*` (`FindShareCard`, `CollectionShareCard`, `ShareQr`) — captured
  off-screen for `view-shot` PNG, never visible to Maestro. System share
  sheets are OS-level too — Maestro can't introspect them either way.

If a future flow needs to anchor any of these, add `testID?: string` to
the props in the same PR — the pattern is in `EmptyState.tsx`.

## Don'ts

- Don't assert on i18n copy. Use `testID` (E2E) or `accessibilityLabel`
  (component tests via `getByLabelText`).
- Don't assert visual variants (active vs inactive class). Screenshot
  diffs only.
- Don't snapshot the rendered tree.

**Exception:** native OS modals (`Alert.alert`, `ActionSheetIOS`,
permission dialogs, share sheets) don't propagate `testID` — the
buttons are rendered by the OS, not RN. For these, `tapOn` by text
is the only option. Keep flows in the en locale (Pixel emulator
default) so the strings match what's in `en.json`. If a flow needs a
non-en locale, switch via Settings first using `testID`s, then assert.

## Text input on Android — out of scope for E2E

Gboard on the Pixel emulator stalls Maestro's `inputText` (autocomplete
intercepts `@` / `.` / `:`, `inputText` hits 120s `DEADLINE_EXCEEDED`).
**Maestro flows on Android don't type into TextInputs.** Cover
text-driven logic at the unit level (`useAuth`, `signInWithEmail`,
`useDiscover` are all Jested in `src/{hooks,services}/__tests__/`).

**For login — tap the "Dev sign-in" button** on the welcome screen
(`testID="welcome-dev-login"`). Rendered only when `__DEV__ &&
EXPO_PUBLIC_TEST_EMAIL && EXPO_PUBLIC_TEST_PASSWORD`, calls
`signInWithEmail` on press; AuthGuard routes to `/(tabs)`.

Reusable flow `maestro/flows/01-auth-bypass.yaml`:

```yaml
- launchApp:
    clearState: true
    permissions: { all: allow } # pre-grant location/camera
- tapOn: { id: 'welcome-dev-login' }
- extendedWaitUntil:
    visible: { id: 'tabbar-feed' }
    timeout: 15000
```

Post-login flows pull this in via `runFlow:` as a preamble.

For other text fields (search, profile-edit), follow the same pattern
— a `__DEV__`-gated button that sets the value programmatically. Don't
reach for clipper / appium-settings / `openLink` deep links / runScript
shell-outs.

## Drift signals

- `testID` is `string | undefined` — typos compile fine. Grep before
  renaming.
- Changing a `useSetting` `SettingName` implicitly renames
  `settings-toggle-<name>` — verify the Maestro flow.
